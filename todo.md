- Notes from the measurements that led there:
  - Godot: `OS.execute_with_pipe("p4", args, false)` streams p4's output to a 50 ms poll loop on Windows, and `OS.kill(pid)` stops it within one poll.
  - p4: `-I` writes progress to a pipe as it happens. Per file it is the local path, ` 15% |`, then five backspaces and the next value, ending ` 100% -<BS>finishing`. `p4 -I submit --parallel=0` prints `add <depot>#<rev>` as each file starts, then that file's percent line.
  - **The catch: parallel transfer silences it.** On the demo server (`net.parallel.threads=8`) a four-file `-I submit` and a four-file `-I sync -q` printed no progress at all. `--parallel=0` brings it back (per-file for submit, a coarse whole-command percent for sync). Open decision: force `--parallel=0`, or keep the server's parallel setting and fall back to a bar with no percentage.
  - Measured later the same day, for parallel transfers (where stdout stays empty until the command exits, tagged records included):
    - **Files done, on disk (sync, any platform).** A file being added appears under its final name at full size at once (preallocated), writable, and turns read-only when complete. A file being replaced gets a full-size `t<n>t<n>t<n>.tmp` beside it that is renamed over it when complete, so the target's mtime changes. With the preview's file list and sizes that gives files done and bytes done, per whole file. In an `allwrite` workspace the read-only signal doesn't exist.
    - **Bytes, from the p4 process's I/O counters (Windows measured).** `Win32_Process.ReadTransferCount` climbed to exactly the 24 MB being submitted; `WriteTransferCount` tracked a 60.9 MB sync. Linux exposes the same in `/proc/<pid>/io` (untested); macOS has no equivalent found. On Windows it needs a helper process, since GDScript can't call the API. A submit option that digests files first (`revertunchanged`, `leaveunchanged`) would presumably read each file twice.
  - P4V's notes: progress for parallel sync since 2023.3 with a 23.1+ server; a busy bar for parallel submit.
  - **Best source found: `p4 --progress=debug`.** Undocumented, in Perforce's published client source since 2021.1. Measured on a parallel sync of 848 files through a pipe: it streams `progress (total|update|done): <local path> (type 2 units 3) - <pos> of <total>` per file while the sync runs, in KB. That gives files done and bytes done with no disk polling and no I/O counters. **Still to test:** the same with `submit`, combined with `-ztag`, on macOS/Linux, and on a pre-2021.1 client (fall back to `-I`).
  - Why plain `-I` goes quiet: progress during parallel transfer is opt-in in the C++ API (`ClientUser::CanParallelProgress()`, default 0). The `-I` handler leaves it off; the debug handler turns it on. P4Python got the same hook in 2025.2. `-G` and `-Mj` never carry progress.
  - The I/O counter is a weaker fallback than it first looked: a 12 MB `binary+F` file was read twice on its first add, so the total isn't exactly the sum of file sizes.
  - Checked later the same day (parallel in effect, confirmed by `transmit` in `monitor show`):
    - `p4 --progress=debug submit` streams the same three lines per file, `type 1` (send), in KB, interleaved across threads but one whole line at a time.
    - With `-ztag` it still works. For sync the records come first and are clean. For submit, extra `... path <name>` / `... type 100` fields appear between records with no blank line, so a tagged submit would need a tolerant parser; the plugin's submit is untagged anyway.
    - **Delta Transfer (`binary+F`).** Submit of a 1 KB change inside a 12 MB file reported `units 5` (deltas) as `0 of 1` then `1 of 1`, not kilobytes. Sync of that change took 0.3 s and produced **no progress lines at all**. So a bar has to read the units field, weight non-KB files by their known size, and snap to complete when the command exits.
    - Unit codes from the client source (`clientprog.h`): 1 percent, 2 files, 3 KB, 4 MB, 5 deltas, 6 items, 7 dirs. Types: 1 send file, 2 receive file.
  - **Test data to obliterate on the demo server** (all deleted at head, about 362 MB of stored revisions as of 2026-10-06): `//gdc_demo_stream/Godot/Skeleton2D/Godot_Skeleton2D/p4godot_*` (41 revisions, 337.9 MB) and `//gdc_demo_stream/Godot/Skeleton2D/Godot_Skeleton2D/p4godot_many/...` (802 revisions, 24.1 MB). No throwaway clients remain.
  - A killed sync leaves that `.tmp` behind and the original file untouched. Cancel has to sweep them. A killed submit goes to `_submit_verdict`.

## Future idea: one machine-wide workspace watcher (not now — Godot first)

- Build the Godot detection behind a "change source" boundary so this service could feed it later.
